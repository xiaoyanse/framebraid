# FrameBraid 后续优化路线图 / Optimization roadmap

[文档入口 / Documentation](README.md) · [当前交付 / Release status](RELEASE_STATUS.md) · [支持范围 / Support](SUPPORT.md)

日期：2026-10-26。核对基线：`5ee707153796cf1d8f9dd7118c664bacf757f97b`（v0.1.0）。

**状态：已确认方向，尚未开工。本文仅规划，不改变当前 ABI、支持承诺或发布制品。**
阶段编号 R1～R5 是实施顺序，不是已确定的版本号、日期或完成率。

English overview: measure first, then improve queue/recovery behavior, reduce unnecessary
copies, improve language/profile integration, and finally evaluate opt-in adaptive batching.
Soak and fault-injection checks accompany these stages. Device discovery and additional
platform/backend acceptance remain separate extensions. This roadmap is not a claim
that planned capabilities are implemented or production-accepted.

## 1. 目标与边界

围绕“采集 → 解码 → 前处理 → 推理 → 结果消费”提高可预测性、效率和接入体验。
优先处理实测瓶颈，不以增加功能数量衡量成果。

- 延续 Media SDK、Vision SDK 两组件及共享公共层，不为此次优化新增第三个 DLL。
- SDK 提供底层采集、处理、资源控制和诊断能力；设备台账、凭据持久化、业务规则、
  报警处理、存储和 UI 仍由宿主负责。诊断事件不扩展成业务报警中心。
- Windows x64 CPU 是现有验收起点；GPU、硬解、其他系统、Java 与移动端不因写入路线图而获得支持承诺。
- 延续有限预算、明确所有权、显式错误、可查询结果和关闭排空，性能不能以破坏这些约束换取。
- 本轮不改源码、生成物、冻结合同、来源指纹或既有标签，也不执行测试负载、操作相机或发布。

## 3. 分阶段范围与验收

### R1：观测与性能基线（最先实施）

目标：解释延迟和资源消耗来自哪里，再决定优化什么。

范围：

- 定义帧序号、流代次、模型身份和请求 ID 的关联；多路和同帧多模型不能串结果。
- 记录接收、解码、入队、出队、前处理、执行、结果可取及消费各时间边界。
  SDK 内端到端延迟与设备曝光到显示的延迟分开；不同钟域不直接相减。
- 统计 P50/P95/P99、帧龄、有效吞吐、队列峰值、丢弃/拒绝原因、内存、线程和外部持有量。
  不适用或不可测标为未知，不用零值冒充耗时为零。
- 优先由基准工具聚合已有指标；新增 SDK 观测采用可关闭、采样且有界的方式。
  不引入监控服务依赖，不在采集/推理热路径同步写文件。

验收要求：

1. 提供可复现负载：单路、预算内并发、超预算三档；固定图片/视频指纹、尺寸、格式、
   采样率、模型及消费者速度。并发档位是测试输入，不是承诺支持路数。
2. 结果绑定源码与 DLL 指纹、工具链、运行库/实际后端、硬件、配置、预热规则和样本数。
   明确吞吐分母、丢帧口径及分位数算法；样本不足时不声称可靠 P99。
3. 队列及帧关联可用于定位至少一次人为注入的慢消费或慢推理；不得把播放器预测结果算成新推理。
4. 对比观测开启/关闭的开销；结项记录测量波动范围，并为各负载选定帧龄、截止时间、
   内存/线程预算和后续性能回归容差。未测量前不预设“提速百分比”。

### R2：队列、重连与故障恢复

依赖：R1 已给出可解释的基线与预算。目标是在压力下保持结果新鲜和资源有界。

范围：

- 分别定义采集帧、压缩包、实时推理、离线批量、结果和控制通知的满载处理。
  压缩包丢弃须保持或重建解码参考链，不能照搬独立图片的任意丢旧策略。
- 统一过期判断、源代次变化、重连退避、慢消费者隔离及回调退出屏障。
- 已接受请求在约定查询窗口内有成功/失败/取消/过期等明确状态；满载拒绝不能伪装已接受。
- 不用无限缓存、无限重试或每帧增建线程处理压力；回调变慢不能拖死整个管线。

验收要求：

1. 覆盖过载、慢回调、结果长期不取、断流、认证失败和反复重连；计数与处置原因可对账。
2. 按 R1 预算验证队列、字节与 SDK 可控线程上限。原生库/驱动内存与 SDK 可控预算分列，
   不承诺外部库 RSS 可由 SDK 硬性限制。
3. 压力解除后在既定恢复窗口内恢复有效处理，队列不持续积压；新代次不混入旧帧/旧结果。
4. 定向候选至少验证 20 次断流恢复、100 次启动/关闭循环；记录失败和重试，关闭排空后无迟到回调。
   次数是测试覆盖要求，不是长期稳定性证明。

### R3：减少复制、重复分配与跨语言搬运

依赖：R1/R2。只优化已确认的热点，不先承诺全链路零拷贝。

范围：

- 画出解码缓冲、SDK 帧、共享池、前处理张量和语言视图之间的复制/分配清单，记录每帧次数及字节数。
- 同进程优先安全引用复用；跨进程共享帧继续可选，不强制所有调用绕经共享内存。
- 评估缓冲复用、转换融合、受控直接写入和 C#/Python 借用视图；不得暴露未完成写入的帧。
- 必要的缩放、颜色/布局转换和 CPU/GPU 迁移单独列账；生命周期安全优先于减少复制。

验收要求：

1. 至少一个基线热点减少实际复制字节或重复分配，并报告相同负载下 CPU、内存、延迟及有效吞吐。
   只有代码形式变化、没有可测收益的复杂改造不能作为性能成果。
2. 输出像素/张量/帧关联与参考结果一致；任何容许误差预先说明，不能只看画面“差不多”。
3. 覆盖借用后异步推理、调用方提前归还、消费者退出、关闭竞争及槽位耗尽；活租约不被覆写或超时强收。
4. P95/P99、预算与关闭行为不超出 R1 确定的回归容差；复杂度或资源上升必须解释取舍。

### R4：跨语言接入与模型档案完善

依赖：前面阶段形成稳定的所有权、错误及统计语义；可先整理需求，但不并行扩张接口。

范围：

- 完善 C#/Python 常用采集与推理流程、错误诊断、结果释放、取消和关闭指导。
  保留底层 API；高层封装不偷偷增加第二层无界队列。
- 明确复制式输出与借用视图：借用须有明确拥有者、只读约束和有效期，不依赖 GC 时机来保障帧安全。
- 统一 profile 版本、模型摘要、前后处理配置及输入输出诊断；仍限定明确模型版本/导出档案，
  不承诺所有 YOLO 模型通用，不建设云端模型注册中心。

验收要求：

1. C/C++、C#、Python 示例从干净解压的匹配 SDK 包运行，覆盖成功、缺依赖、形状错误、背压和关闭。
2. 多模型、异步回调和借用视图不发生串帧、泄漏、二次释放或释放后读取；误用有明确诊断或使用约束。
3. 五类档案分别准备合法取得的代表模型，绑定权重摘要和导出配置，核对预处理与实际输出。
   外部模型缺失时保留未验项，不能用 Identity 图或单测代替五类真实模型端到端验收。
4. 档案更新有兼容矩阵和不兼容错误；头文件、语言封装、能力查询及示例保持匹配。

### R5：条件化 batching 与后端调度

依赖：R1～R4 有实测基线和明确模型合同。目标是验证有收益的调度，不默认改变实时策略。

范围：

- 自适应组批显式启用，仅组合兼容模型版本、后端、形状及前处理约定的请求。
  设置最大批次、等待窗口、截止时间及总资源预算；实时与离线用途分开。
- 不从动态尺寸猜 batch 轴，不擅自给固定 batch 补虚假样本；不满足条件时沿用已声明的拒绝/回退合同。
- 后端选择与切换受调用方策略和能力/资源检查约束；报告实际后端、切换原因和恢复状态。
  不静默重放已完成请求，也不因切换重置帧身份或扩大线程预算。

验收要求：

1. 在兼容的代表模型和多路负载上，对比开启/关闭后的吞吐、等待、P95/P99、帧龄及内存。
   吞吐增加但违反实时延迟预算不能认定为实时优化通过。
2. 覆盖不满批、固定/动态 batch、不兼容形状、过期、取消和并发公平性，逐项回执及结果关联保持正确。
3. 覆盖后端缺失、初始化失败、竞争和允许的回退；未具备 GPU/加速器环境的项目继续标未验。
4. 新调度可关闭并回到既有策略；回退不能隐瞒失败或造成重复完成。

## 4. 持续运行与故障注入：贯穿各阶段

优先构造可控故障和核对恢复结果，不以“跑了一段时间没崩”代替机制验证。

| 故障/压力 | 需要观察的结果 | 主要阶段 |
| --- | --- | --- |
| 网络抖动、断流、认证失效 | 有界退避、状态明确、不忙循环，恢复后代次正确 | R2 |
| 慢消费者、慢回调、结果不取 | 背压/丢弃有原因，队列与外部持有分别可见，正常消费者不被拖死 | R1/R2 |
| 持有共享帧不归还、消费者异常退出 | 不覆写活槽位、不释放后使用；拒绝/故障退化符合合同 | R3 |
| 模型无效、运行库缺失、推理失败 | 错误可定位、失败责任可查询，不崩溃或假成功 | R4/R5 |
| 高并发、关闭时仍有请求、反复装卸 | 截止时间有效、请求收口、回调排空、SDK 对象回收 | R2～R5 |
| 观测消费端停滞或关闭观测 | 指标通道有界，数据处理不依赖监控端在线 | R1/R2 |

验证分层：

- **日常改动**：最小受影响测试及编译/合同检查；文档改动只做内容、引用与不变项核对。
- **阶段候选**：固定基线负载、相关故障注入和新旧结果对比。因新增失败再扩大验证，不循环跑无变化全量。
- **关键稳定性候选**：建议在 R2 首次具备完整恢复机制、R3 内存路径变更后运行至少 4 小时混合负载；
  同一候选同时覆盖两个阶段时可合并一次，报告不能冒充另一候选结果。
- **生产试用前候选**：至少一次 24 小时代表负载，包含压力、故障注入和恢复段。
  这些时长是拟定验收要求，不是 SLA，也不取代现场试用。

长跑须报告预热与稳定段的内存/句柄/线程趋势、尾延迟、失败/恢复次数、队列与外部持有量。
不能仅用首尾内存差证明无泄漏；异常增长应给出归属和解释。底层库允许常驻，不等于 SDK 对象可无限累积。

样本、故障注入与测试库使用隔离目录/随机本机端口；实机操作需另行授权。
结束后回收生成的大样本及测试副本，保留精简原始数值、日志、摘要和源码/制品指纹。
归档无法取得时标明证据缺口，不把摘要当成原始日志仍存在的证明。

## 5. 后续扩展池（不进入前五阶段的必交范围）

| ID | 候选方向 | 拉起条件与验收边界 |
| --- | --- | --- |
| E1 | 自动设备发现、跨品牌探测与参数建议 | 有明确部署需求再设计；扫描由调用方显式启动并限定网卡/范围/超时，区分发现、认证、可取流，不能把探测成功等同设备健康；不持久化设备台账/凭据 |
| E2 | 加速后端、硬解及设备缓冲共享深化 | 有目标硬件和可复现收益；分别核依赖、格式、同步、回退与资源释放，不从 CPU 或普通共享帧结果推导 GPU 零拷贝 |
| E3 | Linux/macOS、移动端及其他语言封装 | 有实际接入方和验证环境；构建通过、运行可用、正式支持分别登记，不提前承诺通用适配 |

这些是可重新讨论的候选项，不是自动实施授权，不绑定交付日期。

## 6. 阶段登记与维护

| 阶段 | 当前状态 | 开工前提 |
| --- | --- | --- |
| R1 | 未开工 | 确认代表负载、测量边界与基准记录格式 |
| R2 | 未开工 | R1 基线和资源/时延/恢复预算可复现 |
| R3 | 未开工 | 有复制/分配热点证据及 R2 生命周期保护 |
| R4 | 未开工 | 所有权/错误语义稳定，代表模型来源与档案明确 |
| R5 | 未开工 | 前阶段结果成立，批次兼容与调度收益有验证条件 |
| E1～E3 | 讨论储备 | 明确需求后重新评估范围与成本 |

- 开工前复查当前代码、上一阶段验证结果和本路线；必要时修订范围，不照搬过期目标。
- 新能力先更新合同/生成器方案，评估 ABI 兼容；不得直接覆盖冻结布局或为通过检查重算历史来源指纹。
- 本路线不初始化新的 OpenSpec 工作流，也不改原宿主的 OpenSpec/计划；实施拆包另行授权。
- 阶段结束记录来源提交、制品、配置、实测结果、失败及未验项；实现、组件测试、实机/现场验收和发布分别登记。
- 只有实际验收后才把目标更新为已有能力。每个阶段可回退，版本号、发布与支持承诺另行决定。
