# SDK量化指标与验收目标 / Performance acceptance

> 2026-10-27用户裁决：完整硬件矩阵及固定4h/24h长跑已移出强制验收，不再作为R1～R5收口阻塞，也不改记为通过。保留已有原始证据；功能、失败回退、资源上限、所有权/取消/关闭定向回归及适用量化继续必验。硬件按实际设备和已声明范围记录实测/未测，不要求穷尽全部设备组合。历史“矩阵/长跑仍待”仅描述旧范围，不恢复已撤销门槛。 详见[范围调整](verification/sdk-acceptance-scope-20261027.md)。

口径版本：**MET-2，2026-10-26**。复核源码基线：`088f821`。这是已确认的R1～R5评价方法修订，不是新性能结果或新支持承诺。

后续实施状态：用户已授权恢复开发；独立S1量化工具与三轮资源/A/A已补，见[实测记录](verification/sdk-met2-s1-20261026.md)。本文第8节的“本轮只改MD”描述原文档收口时点，不代表恢复后仍无新工具；旧工具/阈值/raw保持不变，S2/H5及CPU卸载收益仍未验完。

**核心原则：按优化目的验收，不能把所有改动都评成“推理更快”。** 解码、转换、推理、排队、跨语言搬运分别测量，再核组合负载。功能可用、资源安全、机制减少、性能收益和生产稳定性分开给结论。

## 1. 两种对照，不能混用

| 对照 | 控制条件 | 回答的问题 |
| --- | --- | --- |
| 同路径改前/改后 | 同后端/设备、输入、模型、输出质量、消费者需求和资源预算；主要变量是实现版本 | 这次代码改造是否减少成本、解决等待或造成回归 |
| 不同后端/策略取舍 | 固定相同业务负载、输出要求与宿主资源包络，分别如实记录线程、设备、运行库及内存；这些差异不是应隐藏的噪声 | CPU、硬件解码或推理后端如何分摊资源，各自适合哪种负载 |

硬解可能增加CPU端RGBA回读延迟，却降低CPU解码时间或提高多路承载；不能因慢于CPU单独判失败，也不能只因使用GPU便认定卸载成功。硬解与GPU推理可能共享带宽、显存和功耗，不能假定互不影响。`PREFER_HW`是既有选择策略，不是自动选择最快设备或动态负载均衡。

“纯压缩转发”“解码输出CPU图像”“GPU设备帧直接消费”是不同交付合同，不相互冒充；第三种当前不作为已实现的全链路零拷贝。浏览器播放/显示节奏不属于SDK内部推理耗时。

## 2. 每包主目标与保护指标

| 指标组 / 负责包 | 主目标 | 必须同时保护 | 证明不足的例子 |
| --- | --- | --- | --- |
| M-HW / R2-H2 | 相同有效交付下减少进程CPU时间，或在相同宿主预算下承载更多合格视频路数；分别报告两种收益 | 帧龄/交付、GPU视频解码/复制/计算引擎、内存/显存、其他消费者延迟、恢复安全 | 只测单帧毫秒；只发现GPU；用更少交付帧降低CPU |
| M-CONVERT / R2-1、R2-2 | 减少无用转换、上下文构造、分配次数及复制字节；热点路径再证资源/延迟收益 | 内容/时间戳/采样、参考链、尺寸通知、外部持帧安全、缓存常驻占额 | 把220→1次构造写成CPU同比下降；把虚拟时钟当真实网络FPS |
| M-TENSOR / R2-3、R2-4 | 减少前处理和语言/共享帧传输中的可避免复制、分配及CPU时间 | 对齐/布局/颜色/坐标/模型容差、输入租约、并发隔离、输出拥有者 | 在计时外搬运后声称零拷贝；把必要格式转换计作已消除 |
| M-SELECT / R5-H5 | 在允许列表、strict和依赖约束内选到可运行后端，可解释失败与回退 | 真实模型执行/精度、探测成本、资源预算、单加速域、未知状态、不重复处理 | 枚举成功当CUDA可用；要求自动策略默认找到最快后端 |
| M-SCHED / R5 | 降低准入/排队/组批等待与过期，改善各路有效处理、公平性或离线有效吞吐 | 逐帧截止时间、成功率/拒绝、总CPU/GPU预算、取消/批次输入寿命 | 批次时间除batch当逐帧延迟；少接受请求后声称低延迟 |
| M-RECOVER / R3 | 故障范围可控、压力解除可恢复、稳定段资源无无法解释的持续增长 | 请求唯一终态、旧代次隔离、有限重试、活租约、关闭排空 | 跑几分钟没崩；首尾内存相同；强收仍在读取的槽位 |
| M-LANG / R4 | 常见接入路径可用且所有权清楚，复制/借用成本透明；五类模型档案正确 | C/C++/C#/Python输出语义、诊断、释放/GC、ABI和包一致性 | 所有语言必须相同耗时；Identity结果替代五类模型精度 |
| M-OBS / R1、贯穿各包 | 让上述指标可复现、可归因且开销可控 | 数据通道不依赖监控端、无每帧同步写盘、未知不填0 | 统计字段存在等于真实赋值；重测工具开销混成算法收益 |

每个工作包选**一个主目标，可附一个次目标**，其余作为保护指标。新增硬件能力可先通过功能/安全阶段，不必伪造性能改善；这种结论不能记为性能优化或整包验收完成。

## 3. 统一测量字典

| 指标 | 口径与单位 |
| --- | --- |
| 进程CPU成本 | 固定稳态窗口内内核+用户CPU时间，CPU-s；同时报墙钟秒及有效交付量。报告CPU-ms/有效帧时必须同时报输入/交付/过期/丢弃数，禁止只看比值 |
| CPU利用率 | 明示可用逻辑并行度N；整机归一比例=CPU-s/(墙钟s×N)×100%，核心等效占用=CPU-s/墙钟s。不能混用0～100%与多核累计百分比 |
| GPU使用 | 按设备标识分别记录Video Decode/Copy/Compute等可得引擎采样及显存峰值/趋势、采样方法和间隔；不同引擎不简单相加，不可测写未知。不是仅记录总GPU百分比 |
| 有效帧/结果 | 内容、关联和代次正确且在本场景有效期内交付给指定消费者的唯一帧/请求；重复或过期交付不算收益。SDK字节交付成功与业务有效分开 |
| 有效吞吐 | 固定墙钟窗口内有效交付数/秒；逐流/逐模型及汇总同时给出。局部函数耗时之和不能当实时流墙钟吞吐 |
| 计数对账 | 输入压缩包、接收/解码帧、到期机会、准入请求、拒绝、丢弃、成功/失败/取消/过期、消费和剩余分别记录。异步窗口必须带期初/期末在途；分发到多个消费者按各自分母，不能把一个输入多份输出叫作更高源FPS |
| 帧龄/响应 | 分列接收→消费者可用、接收→实际消费；推理分列submit→结果可取及submit→fetch。源PTS需可靠钟域映射才可计算媒体帧龄，否则只报同域接收后时长，不称曝光到显示 |
| 分段时间 | 网络接收、解码、硬件→CPU传输、颜色转换/缩放、入队等待、前处理、ORT Run、后处理、结果等待/语言复制分开；冷启动/预热/稳态/恢复分开，不跨钟域相减 |
| 延迟分布 | 同一边界的P50/P95及样本量/测量分辨率；P99须有足够尾部样本与重复性说明，否则仅描述观察值。三轮相似不自动等于统计显著，毫秒字段不伪造微秒精度 |
| 内存/分配 | SDK池、队列、中转、外部持有及缓存常驻占额，与进程私有内存/工作集、原生库堆、驱动显存分别记录。次数/请求字节不等于实际峰值；池化可合理增加有界常驻量 |
| 恢复/关闭 | 故障可观测时刻→首个正确且新鲜输出，并报重试次数/额外资源；另报恢复到持续达标的窗口。关闭完成时刻、SDK工作线程和迟到回调单列 |

进程CPU含语言调用方、SDK和进程内运行库，无法归因时不可称SDK独占CPU；外部造流器/服务进程负载单列。采样不到GPU计数不自动判功能失败，但**CPU未测不得宣布卸载收益**；缺少资源竞争观测时不宣布完整承载收益。

## 4. 最小场景矩阵，不做全组合穷举

| 场景 | 固定内容 | 主要判断 |
| --- | --- | --- |
| S0 压缩转发 | 固定H.264/H.265真实GOP与时间跨度，纯压缩消费者、慢消费者分别测 | 不为像素探测启动解码；直传交付、队列、关键帧重同步 |
| S1 全帧CPU像素输出 | 起点1080p/30 FPS，单路，再按预算增加路数；CPU与硬解都交付同格式/尺寸 | CPU卸载、回读、帧龄、GPU资源与合格路数；720p/4K仅目标场景需要时加 |
| S2 检测采样与混合消费 | 固定输入30 FPS，5/10 FPS像素消费者，混合30 FPS预览；网络节拍实测与虚拟时钟分列 | 转换次数、有效采样、抖动与各消费者等待，保留参考链 |
| S3 推理后端 | 代表模型/档案固定，单模型和按需多模型；CPU基线、实际具备的加速EP | 真实执行/数值容差、资源、稳定运行；策略按用户优先级，非自动竞速 |
| S4 端到端组合 | 单路→预算内多路→超额三级，采集+解码+采样+推理+取结果 | 截止违约/帧龄、有效交付、CPU/GPU竞争、健康流公平性；源/模型组合明确 |
| S5 故障与资源安全 | R3断流/慢消费/缺依赖/持帧/关闭的相关定向场景；无固定时长门槛 | 资源包络和恢复，无重复/悬空/代次污染，不以故障低吞吐与正常负载比较速度 |
| S6 跨语言复制/借用 | 同帧/模型、匹配包与绑定，复制/借用分别调用 | 字节与拥有者正确、额外复制成本和生命周期，不要求GC/Rust两种运行方式同速 |

路数是实验变量，不预先承诺4/8/16路。可承载路数是**在指定模型/码流/输出/预算下，所有要求的流在指定窗口同时满足交付与延迟条件的最大已测档位**；未扫到上限只写“已测到N路”，不虚构最大值。必须记录源本身不足供帧、OS/电源/其他负载干扰和各流最差表现。

单IDR重复、Identity图、虚拟时钟仍用于定位/回归，不能替代S1真实GOP、S3真实模型和S4整链；RTSP读取、SDK解码、浏览器WebCodecs是不同层，不把SDK结果直接当看板体验验收。

## 5. 目标卡：测前确定，不先编提速百分比

每个候选/目标场景填写一张小表，首轮缺数据就标待标定，不能生成已通过结果：

| 必填项 | 内容 |
| --- | --- |
| 任务/场景与对照 | 优化ID、S0～S6、同路径回归或跨后端取舍、基线/候选身份；功能/安全/收益哪个是本轮交付 |
| 输出与有效性 | 输入供给、GOP/profile/位深、输出尺寸/格式、各流目标FPS/新鲜度、模型/档案/容差、消费者行为 |
| 主目标 | 如CPU-s/固定窗口降低，或合格路数增加；机制任务可选择减少转换/复制，不外推系统收益 |
| 保护预算 | 当前公开/配置硬限；另列该场景允许的帧龄/截止、最低有效交付、各流公平性、内存及恢复窗口，注明来自接口合同/需求或待标定实验值 |
| 有意义改善/回归 | **绝对影响量+相对比例+重复性**，依据A/A环境波动及实际使用影响，在测候选前定；不可只拿统一5%作验收线 |
| 程序与证据 | 热身规则、稳定窗口、轮次和实验时间/次数预算、样本/分位算法、CPU/GPU采样方法、观测开关开销、失败/停止条件、raw证据位置 |
| 未知与结论范围 | 不能测的资源/硬件/模型，是否限制收益证明；功能、收益、长期稳定性分别签结论 |

已有`perf-budgets.json`中的20/50/100ms和64MiB调查线等，**仍是历史特定工具/合成负载预算**；不改原值、不外推成所有实时应用SLA。本轮不补填未经实测的CPU节省比例、支持路数或GPU收益。真实应用新鲜度/延迟诉求未明确时，先输出实测包络/待确定目标，不冒充最终生产验收。

## 6. 测量与判断步骤

1. **先冻结场景与硬底线。** 内容/模型精度合同、输入/帧身份、拥有权、队列/字节/线程硬限、唯一终态、关闭安全不能为收益放宽。不同硬件转换路径按测前定义的像素/模型容差，不强求无依据的全RGBA字节相同。
2. **补A/A可重复性。** 相同实现/制品在相同条件下重复，记录绝对波动、相对波动和观测成本。之后交替运行基线/候选，三轮可作起点，不是万能统计保证。同基线/环境已有可靠标定可复用，不每提交重做；达到目标卡停止条件或无法分辨时记录结论/缺口，不无限重测直到变绿。冷启动与热稳态不能混比；稳定窗口长短/样本量写目标卡，必要时扩大，不每次提交重跑全部矩阵。
3. **核计时边界。** 每轮完整保留分母、失败/拒绝/丢弃/期初期末在途；轮询/消费等待不能当ORT耗时，计时外搬运不算消除。原始数据、慢轮和失败轮不删除，不选最好一轮。
4. **分两道门。** 先核功能/安全及场景硬预算；再判断主目标改善是否超过波动且有实际意义、保护指标是否在预算内。跨后端资源取舍不要求所有指标同时变好；违反已定硬底线时不能以CPU下降抵销。
5. **处理5%旧警戒。** 旧工具触发事件保留；以后可作为兼容观察标签，不自动判回归成立或验收失败。确认回归需同路径、可靠测量、重复性及测前绝对/相对影响判断；超过硬预算则独立处理，不能拿“样本噪声”忽略。修订口径不自动关闭R2-SAMPLE-02或H5-CORE-PERF-01。
6. **无证据不判胜负。** 收益落在噪声内→收益未证；只实现机制→机制已验证；CPU降低但延迟增加且符合需求预算→明确取舍。没有适用场景目标则只能保存检查点，不能事后为既有候选量身改线。

## 7. 结论与分阶段门槛

每份记录分别列“功能/安全”“主目标收益”“保护指标”“未验项”，允许功能通过而收益证据不足：

- **功能/安全已验证**：限定输入、设备和接口，不等于性能收益。
- **机制已验证**：转换/复制/分配或准入阻塞事实改变，尚未外推CPU、承载或整链收益。
- **收益已证实**：目标卡主指标有重复且有实际意义的改善，保护指标满足场景预算。
- **资源取舍已量化**：如CPU成本下降但回读延迟增加，逐项说明是否适用；不是普遍更优。
- **证据不足/待复核**：缺CPU/GPU、真模型、A/A、可靠样本或现场需求，不用未知填0。
- **回归/预算或安全违约**：分别写证据和整改，不混成一个总分。

| 阶段门 | 要求与实际状态 |
| --- | --- |
| M0 文档收口（本次） | 修订目标与对照口径、回审历史结论、保留raw及未验项；不运行新测试、不改代码/阈值 |
| M1 恢复开发前的量化前置 | 优先为下一包填目标卡、A/A及缺失测量项；H2先补CPU卸载/回读及混合负载，H5按模型可用与失败恢复，不一次扫完所有组合。现有工具需要的补测/改造仍未做，任务归R1 |
| M2 工作包候选 | 按目标卡做局部+相关S场景，功能、安全与收益分别验；未达收益可保存机制成果，但不能把工作包整体验收勾完 |
| M3 稳定候选 | 同候选相关功能、故障恢复、资源边界和关闭定向验证；不要求完整硬件矩阵或固定4h/24h长跑，不用未做长跑阻塞收口 |
| M4 发布/宿主升级 | 独立授权和匹配包/硬件/模型验证；本次无发布、不改AM-RT固定依赖 |

## 8. 迁移与当前工具边界

MET-2口径自本次文档提交起作为下一轮评价依据，**不是对历史raw重新写结果**。原测试阈值、JSON、图表、DLL和来源/ABI冻结不变；历史记录原文加新口径通知及复核说明，差异见[复核表](verification/sdk-metrics-review-20261026.md)。

当前工具仍主要输出历史局部/合成时间及5%告警，CPU时间/GPU引擎、真实GOP组合和A/A并未全部接入。本轮只改MD；恢复开发后先按R1新增前置补齐适用工具/基线，不能直接把旧比较器输出当MET-2验收。SDK支持范围、API和能力位不因指标文档变化扩大。
