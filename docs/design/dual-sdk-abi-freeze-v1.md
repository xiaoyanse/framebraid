# 双SDK C ABI 1.0 实施冻结记录

2026-10-25用户授权继续收口合同并实施DLL/共享帧；本文件登记**设计与接口冻结**，不替代SDK-G0～G3、硬件或用户验收。源码核对提交为`de16e58`（完整提交由Git查）；此前头文件/类型、后处理分别见`d35444e`、`a742fec`。历史回审及候选讨论保留，不再作为当前待决状态。

## 1. 冻结工件与变更规则

- ABI版本1.0，121个签名及74个公开结构以`sdk/include/`为实际头文件；同源Rust值类型在`am-sdk-abi`。Windows x64自然对齐，禁pack(1)、Rust结构体跨边界或C++异常穿越C ABI。
- 数值、能力位：`sdk/abi/constants.json`及类型附录§6.2；预算唯一数值源：`sdk/abi/defaults.json`。字段和错误码在冻结前补充`internalError=28`，原生访问违规、无效指针、进程退出不承诺恢复。
- 布局：`sdk/abi/layout-win-x64.json`，现有74个C/Rust对照测试含547字段偏移；其他平台不据此签收。
- 五类样本及导出身份：`crates/vision/resources/profiles.json`。独立后处理参考已验证；完整模型参考输出在实现期另入验证夹具，不把“待运行”当设计缺档，也不把后处理测试当模型运行验收。
- `sdk/abi/freeze-v1.json`登记以上文件SHA及本合同，`node scripts/sdk/freeze-abi.mjs --check`禁止静默漂移。未对外发布前发现错误须补审计、重生工件和记录；对外交付后遵守ABI主/次版本规则，不能靠重算哈希偷改同版本语义。

## 3. 默认/零值、队列与生命周期细节

- `get_limits`给出本库支持字段，非本库字段为0；`set_limits`仅可继续收紧当前值，不能重新放宽；0表示阻止新准入，不是无限。已有资源不因收紧而销毁或解除责任。共享cfg显式非NULL时容量字段必须非零。
- 六类队列都设项/字节/等待者上限；默认等待者16、单次等待最多5s。实时帧推2/拉8项及32MiB；编码36项/8MiB；实时请求每模型×槽16、域64及64MiB；离线单次64、域64及64MiB；结果256项/64MiB/60s；控制32项/64KiB。控制查询/取消/关闭不排入数据队列。未用类别明确notSupported。
- 样例压力算账：1080p RGBA单帧8,294,400字节，默认帧域96MiB最多容纳约12份此类帧；16路只是源数量上限，不能据此宣称16路都可同时保留任意队深。共享4槽64MiB与普通帧预算分别计；绝不通过多ctx/旧池失联把实际映射藏在当前有效帧字节之外。
- 句柄登记、关闭屏障、销毁隔离分别计费；隔离区保留小型分配令牌才能保证地址不复用，不能只记地址却立即释放分配。ctx关闭按子先父后，外部帧/结果/统计缓冲及共享租约排空前保持CLOSING；CLOSED后查询和幂等close有效，destroy仍要求先销毁子对象。destroy后使用属于UB。
- 关闭0为非阻塞；共享borrow/publish等待上限包括取锁时间，没有“先无限等锁，再等5秒”的隐藏路径。等待循环不持互斥量休眠，不按帧创建线程。非阻塞时锁忙也返回tryAgain，不产生迟到发布/租约。
- 结构输入指针必须指向声明的可读内存，输出指针指向声明的可写内存；SDK校验size/范围/对齐/值，不承诺拦截任意野指针。旧init最小完整前缀按公开旧布局接受，未含完整feature_flags默认0；未知位拒绝。输出不越过调用方size，保留调用方struct_size。
- RAW模型无可证明的batch轴时`native_batch=0`，不猜第一维是batch；动态模型公布SDK包络与模型约束的交集，字节预算同时生效。自动攒批/固定batch尾项填充继续不做，尾项明确拒绝。

## 4. 冻结与交付的区别

6.1按本记录收口，可开始稳定导出层；6.2/6.2b/6.2c、G0～G3保持各自未完成状态。开发阶段能力位只报告实际实现/编入的能力，DLL导出子集必须列清；只有最终全部首版入口与行为验证后才可称为SDK交付。源码不引入业务、数据库、PLC、Web播放或网络分发层，也不影响AIeng及其他讨论待办。

## 5. 发布前冻结修订r2

实际外部调用绑定时发现，原六类队列的get/set只有文字，没有C函数声明。此次补齐两库对称的4个签名（总117→121），实现逐类查询/仅收紧及非法类/非本库类的明确拒绝；不改变已有签名、结构或数值。此前冻结指纹原字节保留在`sdk/abi/history/freeze-v1-r1.json`，新指纹ID为`am-sdk-cabi-1.0-20261025-r2`并记录前指纹摘要。当前仍是首次对外发布前的开发版本，无已发布消费者；G2最终需核齐121个实际入口，不能据开发子集签收。

## 6. 发布前绑定数值修订r3

真实解码DLL实调发现，constants.json错误地把像素枚举记录成位图1/2/4/8，而C/Rust头文件一直为0/1/2/3；Python生成器重复输出导致后者被覆盖。现将机器常量源修正为枚举0/1/2/3，能力位图仍采用1<<枚举值；生成器禁止同名数值冲突和重复覆盖，增加跨源检查。现有C函数、布局与C/Rust枚举数值均不变，不增加函数。原r2指纹保留于history，r3关联前指纹；此为未对外发布的开发绑定修复，不声称已发布ABI可随意改值。

## 7. 发布前初始化语义修订r4（用户确认）

用户确认保留纯共享帧场景：显式AM_INIT_SHARED_FRAMES且runtime_dirs为空时，推理SDK可只提供共享帧借用/归还，无需安装ORT；这不代表可执行模型。提供runtime_dirs时必须在amv_init校验并加载，失败不给ctx；首次推理运行库失败后新推理init仍报原故障，只有显式backend_retry成功才恢复。重试要求所有ctx已destroy（包括CLOSED未销毁者）；共享帧ctx也须先关闭销毁。已有正常运行库后的配置错误不污染其他ctx，禁止换用不同路径的ORT或混合OpenVINO/CUDA。

后端行的provider_loadable/verified以本进程实际成功会话/真实推理观察为证，未观察为0并用note注明未知，不通过探测偷偷选择加速后端；这不替代SDK-G3包级环境矩阵。OpenVINO首版固定CPU设备并显式限制provider线程，其与ORT线程的保守配额都入账；原生辅助线程/RSS未提供的观测不得假称严格实测。

121函数、74结构、547字段、枚举和预算均不改；仅发布前语义澄清，ABI仍1.0。r3原字节保留history/freeze-v1-r3.json，r4关联其摘要，实际运行门继续独立登记。


## 8. 发布前原生运行库寿命修订r5（2026-10-26用户确认）

首版允许ORT、FFmpeg等底层运行库由宿主进程持有，退出时统一回收；不要求在单个SDK模块卸载时强制卸载底层库，不在DllMain执行阻塞join或猜测引用计数后FreeLibrary。SDK模块与依赖寿命分开：全部SDK对象关闭销毁、外持图像/结果/映射归还、回调屏障完成、SDK自有工作线程退出join后，两个SDK DLL仍必须支持安全卸载和重载。依赖在驻留期间不得保留指向已卸载SDK的回调或SDK自有工作线程。

同一宿主进程不通过卸载SDK来切换ORT路径或不兼容provider；既有路径/后端冲突仍明确拒绝，需要切换时重启进程。反复装卸须记录预热后的私有字节、句柄及SDK工作线程走势，核实没有持续增长，不能用“常驻”免责，也不能用一次CLOSED代替模块实测。有限轮Windows CPU测试不代签加速平台或7×24现场耐压。

此为用户确认的发布前依赖寿命边界调整，不改121函数、74结构、547字段、枚举或预算，ABI仍1.0。r4原字节保留history/freeze-v1-r4.json，r5关联其摘要；运行验收按实际证据登记。
