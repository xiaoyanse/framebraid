## 为什么做这件事

下游探针全程绕开 SDK 用裸 onnxruntime/openvino 拼出了完整的开放词汇检测方案，说明两件事：

1. **需求真实存在**：现场类目（防护服/防毒面具/手）不重训模型直接检测，是下游当前就要用的能力。
2. **SDK 缺口具体**：探针里每一段绕路——词表烘焙脚本、解码 numpy、ROI 二次推理拼装、量化脚本、双引擎对比页——都是业务层在替 SDK 干活。这些工作量收进 SDK，下游接入从"一周探针"缩到"一次配置"。

## 痛点 → 能力映射

| # | 下游探针中的实际做法（痛点） | 提议的 SDK 能力 | 优先级 |
|---|---|---|---|
| A1 | 手写 Python 脚本把词表嵌入烘焙成单输入 ONNX（`bound-local-*.onnx`），换词表=重新烘焙 | **词表绑定/重绑定**：SDK 内置 CLIP 文本编码 + 词表→嵌入→绑定检测模型，运行期可换词 | 高 |
| A3 | 社区文本塔与检测模型嵌入空间不配对，检出全落在 letterbox 填充带；未归一化输入产生饱和假分（本会话 SDK 复测确认） | 首批：维度校验和文档警示；嵌入空间健康度探测为后续能力。维度匹配不证明空间配对。 | 高 |
| B1 | 每个测试脚本各手写一遍 YOLO 头解码（cxcywh→xyxy、sigmoid、NMS、逆 letterbox） | **RAW 模式通用检测头解码**：声明输出布局后由 SDK 解码，输出结构化框（复用既有五类结果） | 高 |
| C1 | 全图检防护服 → ROI 外扩 15% → 二次推理检手（手最高分 0.167→0.461） | **ROI 级联推理**：一次提交全图+ROI 规则，SDK 内完成裁剪、二次推理、坐标回映 | 高 |
| A2/B2 | 6 个手部提示词（hand/human hand/bare hand/gloved hand/glove/protective glove）在业务层合并去重统一为"手"，框数 7→15 | **提示词组**：一个逻辑类目绑定多个提示词，SDK 端按组输出并跨提示词去重 | 中 |
| D1 | onnxruntime.quantization 静态量化 + 校准脚本；INT4 偏置溢出需人工修正（W4A8+浮点偏置） | **量化工具链**：FP16/INT8/INT4 转换 + 校准数据管理 + 转换后精度回归验证 | 中 |
| D2 | 运行剖析发现 FP16 卷积在 CPU 实际转 FP32 执行、INT8 仅部分卷积走整数内核——文件标签不等于执行精度 | **实际执行精度报告**：扩展现有 selection report，报告各算子类实际内核精度 | 中 |
| E1 | OpenVINO 首次加载 2.9s（ONNX→IR 转换编译），每次进程重启重付 | **模型编译缓存**：编译产物落盘缓存，二次启动免转换 | 中 |
| E2 | 手写双引擎（ORT/OpenVINO）同文件同口径对比页（预热+三次中位、逐图并排、明细表） | **引擎对比基准工具**：SDK 自带跨引擎/精度/输入尺寸的基准跑批与报告生成 | 低 |
| F1 | 模型下载来源+SHA256 手工维护 manifest.json | **模型资产清单**：来源/指纹/配对关系随模型档案登记（复用既有 manifest 思路） | 低 |
| A4 | 中文显示名与英文提示词的映射在业务层维护，界面改名会导致规则过滤不一致 | **类目显示名与提示词分离**：档案级"显示名→提示词组"配置，结果按显示名输出 | 低（可并入 A1/A2） |

与既有登记的关系：C1 对应 ROADMAP「ROI 区域裁剪推理」的细化；C1+C2（阶段间衔接）对应「多模型流水线」的检测特例。v0.3.0 已具备的底座：张量入口（双输入已实测）、raw_preprocess 声明、五引擎与热切换、selection report——上表均为在其上的增量，不推翻既有合同。

## 关键设计输入（来自探针的实证事实）

实施时直接采信的事实，避免重新踩坑：

- **文本编码器必须与检测头配对**：worldv2 权重 + 异源（尤其量化版）文本塔 = 嵌入空间错位，症状是高分框集中在 letterbox 填充带、类别系统性偏置。首批维度校验无法拦截此类语义错配。
- **图像输入必须 /255 归一化**：未归一化输入会产生接近 1.0 的饱和假分，看起来"检测正常"实则无意义。RAW 张量入口不代管预处理（合同如此），但 A3 类校验或文档必须显式提示。
- **裸词优于模板**：该权重组合下 `a photo of a {}` 模板分数崩至 0.019，裸类名 0.69。提示词组（A2）默认词表不应预设模板。
- **小目标靠 ROI 放大而非提分辨率**：全图 640 手 0.167，ROI 放大后 0.461；整图 1280 仅 0.167→8 框（vs ROI 路径 15 框）。C1 的价值依据。
- **量化在 CPU 上的真实收益是内存不是速度**：INT8 文件 -74%，但 ORT CPU 上 INT8 反慢约 25%（量化反量化开销）；OpenVINO 上 INT8 略快于 ORT。D1/D2 的验收口径必须含实际内核报告，不得以文件大小或标签宣称加速。
- **多提示词是召回的主要手段**：单 hand 提示词漏检过半，6 词组去重后框数翻倍（7→15）。误检（glove 命中裸手）同时上升——A2 的去重输出需保留原始命中词供业务过滤。

## 边界与非目标

- **不做合规判断**：探针明确保留"glove 误检裸手"类结果给业务层裁决；SDK 输出检测事实，穿戴合规/SOP 规则是宿主职责。
- **不做文本编码器训练/微调**：只消费现成文本塔，配对校验为准。
- **不改变 RAW 张量入口合同**：A3 是校验与诊断增强，不是隐式预处理。
- **量化工具不进运行库**：D1 属离线工具链（scripts/sdk 侧），运行库只消费量化产物并如实报告执行精度。

## 实施路径建议

1. 先 A3 + B1（拦截假检出 + 免手写解码）——最小改动、最高频痛点，且都有本会话复测证据可直接转化为验收用例（填充带假框、饱和假分、解码对拍）。
2. 再 A1 + A2（词表绑定与提示词组）——需要 ABI 合同先行（`docs/design/dual-dll-abi*.md` 增补词表/提示词组结构）。
3. C1 级联推理随「多模型流水线」统一设计，不单独开口子。
4. D/E/F 按下游实际使用节奏启动，量化工具链优先于编译缓存。

每项启动时按门禁分级（预期 L2～L3：涉及公开接口与跨模块行为），验收引用 `docs/PERFORMANCE_ACCEPTANCE.md`。
