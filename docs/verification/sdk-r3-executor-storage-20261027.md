# R3：共享推理执行器常驻存储与有界快照

## 范围与改前证据

评审基线`f3bbfcbfc3b2d1092dccb34a61189a338f54855d`，对应R3 1.1l和预算矩阵BP10的执行器部分。MET-2 M-RECOVER/S4-S5主目标为固定实际Job/句柄槽、索引常驻及扩容重叠完整计费；保护分类隔离、ID提交/替换顺序、取消、关闭和通知。只改SDK，不改AM-RT、不连现场设备、不发布。

旧执行器队列和Context索引没有独立保留容量账，索引清理每轮clone一个Vec，统计另collect一个Vec。改前新增的真实执行器容器测试已失败：配置3个Job槽，填入3项后capacity=4；本机Rust单测Job=224字节，槽存储896字节。测试用不可运行的Context条目占槽以隔离容器行为，不冒充真实模型推理；有效Job/生命周期由后面的真实DLL检查覆盖。

## 实现与定向量化

- Job队列按现有domain_infer_slots固定预留，线程句柄也先预留；Engine本体、这些槽和Context索引capacity记为storage_bytes，与在途暂存共同受现有64 MiB执行器总额限制。Context/实时/离线分类账不承接共享存储，不提高任何上限。
- 索引增长先核原存储+新缓冲+在途用量，准入后分配精确容量，移动Weak引用并销毁旧Vec后才更新保留额度。移除退役引用不归还仍保留的空闲容量。登记在替换旧请求、插入记录及发布ID前完成，拒绝不改这些状态。
- 清理以16项固定栈数组取得短期Arc引用，在域锁外try_lock记录表，跳过正忙的表；查询API仍自行核TTL。小Context集合只取一次快照锁，统计直接fold，不收集临时Vec。不在域锁内调用推理或外部拥有者回调。

| 单测场景 | 结果 |
| --- | --- |
| 3个Job槽 | capacity由4变3，本机单测槽存储896→672字节；输入/线程上限不变 |
| 2 worker/3槽，空索引 | 本机单测完整基础存储920字节；含Engine本体及句柄预留，不含allocator/native内存 |
| 索引从4槽增长到8槽 | 先核旧+新重叠；额度差1字节拒绝，长度/容量/保留账不变；放开后增至8槽/总账984字节 |
| 退役4个Context，仅留1个 | 索引capacity仍8、存储仍984字节，不退空账 |
| 输入暂存耗尽总额剩余部分 | 再加1字节拒绝；输入释放后inflight/bytes为0、基础存储继续计费 |
| 一个记录表持锁 | 清理线程仍返回并清掉另一Context的过期记录，无锁序反转或无限等待 |

这些是本机Rust布局与逻辑预算实测，不能当成跨平台固定常量或Release私有布局ABI；更早准入和提前分配是明确代价，不宣称RSS必降。Vision全特性单测18项、无默认特性单测17项全部通过；分类账边界单测使用不分配容器的隔离账本，真实存储另由上述用例覆盖，没有用假账本代验真实执行器。测试编写时的slot类型和scoped闭包编译错误保留，不计为SDK运行故障。

## 性能观察与有限复核

先保存旧DLL并运行既有Identity C往返基准：每轮20次预热、32次突发，单请求/预算内4路/32路超预算慢消费/关闭观测四场景，各三轮。计时包含Python轮询和消费等待，不是YOLO或纯ORT耗时。

初次候选单请求第二轮P95=9.4005ms，慢消费三轮P95=24.2638/35.4061/28.6338ms；旧基线慢消费20.8130～21.1209ms，原始慢轮完整保留。检查发现初稿为获取索引长度额外取一次域锁，已合并长度和首块快照，但没有把它认定为全部波动的唯一成因。

修改前写入followup-target，限定只做两组近邻B/A复核，不反复测到通过。每次仍是完整四场景三轮，最终六轮P95范围：

| 场景 | 最终候选 | 近邻旧基线 |
| --- | --- | --- |
| 单请求 | 1.0309～1.1378 ms | 1.0538～2.0795 ms |
| 预算内4路 | 0.9864～1.1026 ms | 0.9762～2.2471 ms |
