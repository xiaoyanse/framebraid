## 场景与结果（四用例 = 2 场景 × 软件/硬件策略）

**断流恢复**（推流→拉帧→杀推流端→重启同路径推流）：
- 断流后管线尾帧在 1.5 秒排空窗口内出尽，其后 3 秒静默期无新帧、进程不崩、`amc_get_decode_hardware_report` 查询仍可用；
- 重启推流后 15 秒内从新关键帧恢复出帧；源 `source_generation` 严格递增（重连换代），上下文 `reconnect_count` 递增；恢复后 pts 单调、frame_id 唯一；
- 软/硬件策略行为一致（硬件用例实际 D3D11VA 解码）。

**关闭竞争**（帧持续在途时关闭源）：
- 订阅存活时 `amc_source_close` 有界排空完成，不撕裂；
- 源关闭后帧/包拉取均返回 `handleClosed`；
- 按对象树合同先关订阅子对象再销毁源（直接销毁带活订阅的源被拒，语义与 shared 池 1.5b 的关闭顺序依赖一致）；上下文外持归零。

## H2.3 父项收口核对

对照任务原文：两入口选择接入（H2.3a 直接解码、H2.3b RTSP 像素订阅）、策略遵循与实际后端可查询（decoder/源硬件报告，H2.3a/b 及本矩阵）、CPU 回退（H2.3a Rext/回读故障、H2.3b Rext 硬件错误后 CPU 恢复）、参数变化设备复用（H2.3c）、纯压缩直传不启动解码器（H2.3b 首次像素订阅冻结前压缩流独立、像素故障不清压缩队列）均有分项证据；本矩阵补齐"完整故障/关闭"的最后缺口（断流静默/关键帧恢复/在途关闭/子父销毁顺序）。**结论：H2.3 收口。**

## 边界

回环单机合成流；不覆盖真实网络抖动/丢包矩阵、断流期间凭据轮换、浏览器播放器（按任务原文不修改）与多路并发恢复。恢复等待上限（15 秒）为测试容错不是产品指标；无性能结论。
