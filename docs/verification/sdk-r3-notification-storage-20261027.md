## 边界与改前证据

前包按完整活条目48字节计费，但VecDeque容量仍可能大于活条目数。改前定向测试在停止后读到capacity=4、预期0而失败；按本机条目大小推算是192字节Vec存储，不含allocator开销。清空元素只归还活条目，不能证明缓冲已释放。这是所有权/预算缺口，不是推理算力不足。

## 实现与定向结果

注册时根据当前控制项、字节及剩余占用计算槽数，先cached_control预留整块存储，再try_reserve_exact；若容量超过预留则拒绝，不扩充预算。存储许可占一个控制项；每个活通知另占一个项和关闭屏障，但不重复计已预付槽字节。排队+忙回调不超过槽数，正常push不扩容。

注销/停止先切断新通知、清待处理项；没有忙回调即销毁Vec并归还存储，有忙回调则等其返回。准备/线程准入/创建失败归还许可；小额度注册明确resourceExhausted，不先启动线程再永久丢通知。预算拒绝新注册时原回调已排空、当前为未注册，可显式重试。取消/关闭与结果终态不依赖通知投递。

| 定向场景 | 结果 |
| --- | --- |
| 47字节，无既有存储 | 分配前拒绝，capacity=0、控制占用0 |
| 48字节、一槽，100次入队/取出 | capacity始终1，控制字节始终48，活项独立计数；第二项明确拒绝，无扩容/重复字节计费 |
| 取空但仍注册 | 空闲槽继续占48字节；不能先退账后保留缓冲 |
| 停止且无忙回调 | capacity、控制项、控制字节均0 |
| 两槽、一个忙回调与一个排队项时停止 | 清排队项但保留存储与忙回调屏障；忙项真实返回后归零 |
| 单控制项/100次重新准备 | 单项不足“存储+活项”而拒绝；正常重新准备/清理每轮归零 |

3项新单测及Vision FFI默认并行全组14项通过；前包的隔离Domain继续保留，不污染其他线程配置测试。以上单位测试核所有权与计数，真实ORT/线程另见下节。

## 真实Release对照与保护回归

同一真实CPU Identity模型、合成输入和脚本目标卡对照：控制通道只允许1项时，旧DLL注册返回OK、SDK线程许可3→4；候选返回8/resourceExhausted、许可3→3。该拒绝发生于注册准入，不作为已接受通知丢弃或推理失败计数。

默认预算下，改前与候选分别完成100次注册→真实推理→等待回调→注销，每次结果逐字节正确、恰一回调；线程许可全程4、不随轮次增长；注销后5次推理无新回调，最后模型关闭后许可0。保护性单次调用耗时P50/P95旧0.04865/0.10480 ms、候选0.05450/0.09730 ms，均满足沿用的≤2,000 ms错误停止线；这不是新的性能SLA，没有A/A显著性证明，不宣称提速。

既有`test-notify-stats.py`的注销等待、忙回调关闭、回调重入和统计所有者回归通过。真实推理压力脚本验证未取/外持结果时健康Context继续、阻塞通知不阻塞同模型和另一模型、共享活槽持有期间另池30次发布及真实推理正确。通知丢弃36次（前包35次）：固定存储本身现占一个控制项，减少一个可用活项；这是按合同保守准入，推理请求和结果不随通知丢失而失败。
