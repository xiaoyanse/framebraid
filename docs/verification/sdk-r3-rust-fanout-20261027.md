# R3 Rust H264Hub 队列与终态收口

## 测前目标及适用范围

源码基线 `b8f22c9`，候选为本记录同提交；MET-2 M-RECOVER / S4-S5。审计发现旧Rust辅助分发只限制包数、种子不计配置项、GOP只计载荷字节；关闭后仍可被投递或配置更新复活，接收在空检查后才创建通知等待，存在丢关闭广播的窗口。

目标卡先于实现保存于 `.local/evidence/r3-rust-fanout-20261027/target-card.txt`。主目标是订阅36项/8 MiB载荷、GOP最多35包且保留字节上限、关闭不可逆且等待可靠；保护参考链、健康订阅和外部已持消息。本阶段不更改C入口、默认C预算、运行库、网页播放器或AM-RT。Rust辅助H264Hub与C订阅走不同路径，结果分别登记。

## 量化前后对照

先增加5项失败回归及仅测试构建启用的精确关闭窗口钩子，生产逻辑未改时运行：0通过/5失败（退出101），保留 `before.txt`。随后修复并扩充到11项针对性用例；H.264域合计32项通过，原始 `after-with-runtime.txt`。

| 用例 | 基线观察 | 候选观察 |
| --- | --- | --- |
| 连续六个2 MiB包，不消费 | 排队载荷峰值12 MiB | 峰值8 MiB，溢出恢复不超限 |
| 配置加36包预滚种子 | 37项，超过36 | 不完整预滚不入队，只先给1项配置；合法35包加配置仍36项 |
| 一个空载荷关键包后追加空载荷非关键包，共1000项 | 仍缓存1000项 | 达项数边界后清该预滚链并等待下个关键帧；终点0项，合法35项边界另验 |
| 重复关闭后又推配置、叠层及视频 | 复活为3项且丢失关闭原因 | 只保留1次终态，再读返回None |
| 关闭恰落在空检查与睡眠之间 | 100ms超时，未收到终态 | 确定性窗口用例正常收到终态并结束 |

这是逻辑排队载荷/项数与错误恢复结果，**不是总RSS降低33%或播放提速**。输入正在被调用方构造、原生库内部和消费者已持消息仍有各自生命周期；共享Arc也不等于所有订阅字节简单相加后的物理RSS。新增载荷检查最多扫描固定36项元数据，不扫描图像内容；未做独立CPU开销收益结论。

## 实现与保护验证

- 每订阅保留36项，新增Rust常量`CLIENT_QUEUE_MAX_BYTES=8 MiB`；配置/重同步计项，视频/叠层/关闭原因的变长载荷计字节。GOP最多35包并继续受调用方有限字节上限约束，种子须从同代次关键帧开始，不分段接上受损GOP。
- 视频压力先移除低优先级叠层；叠层只留最新一项。仍溢出则清受损包链、保留当前配置并发一次重同步提示，等待新关键帧；有消费就清停滞计数，无消费连续两次溢出以1011结束。过大单包以1009/`media.packetTooLarge`结束该订阅，不错误归因于慢客户端。
- 关闭与全部投递/配置操作共用队列锁；归还旧排队引用，只保留一次终态，后续生产者不得复活。消费者先登记Notify，再在队列锁内一起读消息/终态；避免丢广播及空检查后跳过刚入队的关闭原因。对照[Tokio Notify官方约定](https://docs.rs/tokio/1.53.3/tokio/sync/struct.Notify.html)；本机锁定Tokio1.53.3，没有增加依赖或开启新生产特性。
- 一慢一快订阅，快端200/200包按序收到；慢端超额关闭不污染快端，外部保留的第一包内容不变。合法最大种子、极小载荷GOP、叠层让位视频不触发重同步、超大单包、8线程共800次投递/配置/关闭竞争通过；两个接收者被关闭广播唤醒且终态恰一次。
- 旧溢出用例原先要求保留已失去关键帧的P帧，已纠正为清受损链；真实消费重同步后从新关键帧恢复，再次过载产生新提示。不通过删断言隐藏新旧语义差异。
