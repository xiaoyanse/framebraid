## F02 — GPU_FRAME 分类档案恒 letterbox（审计 P1）

**裁决：实施 a（kernel 支持 center crop），不做准入拒绝。** 评估：改动=PTX 加 4 个 `.param`（crop 标志/crop_x/crop_y/crop_scale）+一段谓词化映射重写（14 条指令，全部为既有指令形态）+Rust 侧传参——属任务书"加参数+坐标偏移的小改"档，且拒绝路线（b）会造成 classify 档案 GPU_FRAME 能力缩水（合同 §4.2 classify 前处理承诺 center crop，§3.3a 未排除分类）。留 a 不留 b。

**实现**：
- `nv12_letterbox.ptx`：新增谓词 `cropen`（crop 参数非 0）；主色路映射重写为 `s=(d+0.5)/crop_scale-0.5+crop_src`——公式与运算顺序逐字对齐 CPU `prepare.rs` resize==2 分支（`(x-left+0.5)/scale-0.5+crop`，left=0；div.rn=IEEE 同 Rust `/`）。边界处理保留在整数邻居钳制（两 tap 塌缩到钳制像素=CPU 浮点 clamp 的等值实现，与既有 e2e 参考注释口径一致）。crop 标志 0 时 letterbox（sampling=0）/ROI（sampling=1/2/3）三模式与旧 kernel 逐指令同路——全部既有调用方传 0。
- `pipeline.rs`：`crop_geometry()` 纯函数（与 prepare.rs 同式同序：max 比例、`floor((src-dst/scale)/2).max(0)` 源域窗口偏移）；`preprocess_to_binding` 增 `center_crop` 参数；classify 分支 rw/rh=dst（无填充带，kernel pad 门不触发）、变换元数据 crop_x/crop_y 如实填充、left/top=0。
- `input.rs`：`capture_gpu` 按 plan 的 `preprocess.resize==2`（GPU 输入仅 PROFILE 模式，档案 classify 即 resize==2）传入 center_crop。

**验证**（门 1 纯逻辑 / 门 2 真机 kernel 级对拍）：
1. `crop_geometry` vs **生产 CPU 路径真调用**（`sdk::prepare`+`Preprocess::profile(dst,true)`，非镜像公式自证）：6 组非方形（640×480/480×640/1920×1080/800×600/224²/123×321→224）scale/crop_x/crop_y/left/top 逐字段相等——`classify_crop_geometry_matches_cpu_prepare_transform`。
2. 真机门 `gpu_classify_center_crop_matches_cpu_mapping`（新 ignore 测试，RTX 5060+CUDA 13 ORT）：640×480 高频条纹 NV12 → D3D11 纹理 → `preprocess_to_binding(…,224,224,true)` → 设备张量回读，对**独立 CPU 镜像**（测试内手写复刻 kernel 语义：Y 双线性+UV 单采样+BT.601 limited+1/255，常数取 PTX 位型 0x3B808081/0x3F950A3D/…；含 kernel 的"x1 由未钳制 floor+1 再 min"边界序）：**max|Δ|=1.79e-7**（容差 1e-4；修复前 letterbox 误映射=完全不同的源窗口，差值在 0.1 量级必炸）。变换元数据与 CPU prepare 逐字段一致同门断言。诊断输出 `scale=0.466667 crop=(80,0)`（640×480→224：源中心窗口列 80..560、全高——正确几何）。
3. 既有 letterbox 真机门复跑绿（`gpu_frame_inference_matches_cpu`，检测级对拍）——证明 launch_route 重构（launch()→launch_region 统一传参）与 PTX 改动对 detect 路径零回归。

**诚实边界**：classify 验证到 kernel 输出张量+变换元数据层（镜像独立复刻 kernel 语义，非共享生产代码）；未跑 classify ONNX 推理级对拍——本仓无 classify 冻结样本模型（`classify-yolo11n-prob-v1` 样本 SHA 已入 profiles.json 但模型文件不在本机夹具）；色路等价由同 kernel 主路径的既有 letterbox e2e 承载。PTX 修改经 cuModuleLoadData JIT 实载验证（sm_120 驱动 JIT 接受；无离线 ptxas 工具链复核——本机 gcc/nvcc 工具链故障为已知环境事实）。

## F03 — 直传设备 0 硬编码与 CUDA 定向脱节（审计 P1）

**裁决：实施接线（按会话实际 ordinal），不做准入拒绝。** 评估：selector→ordinal（device.rs resolve_targets）已是 ABI 1.6 合同能力，接线为机械改动（5 个硬编码点+缓存键），拒绝路线则把已承诺能力砍半。单 GPU 机无法真机验证非 0——按"代码可达性修复+单卡 ordinal 0 回归"口径登记，双卡未测。

**实现**（5 个脱节点全接）：
1. `driver_sys.rs::establish_context(ordinal)`：`cudaSetDevice(ordinal)`（原 0）——primary ctx 激活路径不变。
2. `pipeline.rs`：`GpuPipeline::for_device(ordinal)` 按 ordinal 键控进程级缓存（HashMap<u32, Result<&'static, String>>；每 ordinal 首次结果含失败缓存=旧 OnceLock 语义；成功管线 Box::leak 进程保活=旧单例寿命语义，泄漏上限=设备数）；`global()` 移除。
3. `registry.rs`：纹理注册缓存从进程全局单表收敛为 GpuPipeline 设备级成员（注册资源绑定创建时上下文，多卡各持 LRU16——单卡行为等价）；`release_for_shutdown` 移至 `pipeline::release_for_shutdown` 逐设备 drain（DllMain/onexit 禁做清理的约束原文随迁）。
4. `iobinding.rs`：`new/new_batch` 增 device 参数→`MemoryInfo(CUDA, device)`（原 0）。
5. `model.rs`：`Model::cuda_ordinal`（selection.selected backend==2 的 device_id，与 device_label "CUDA:{n}" 同源；非 CUDA 恒 0）。

消费点：`capture_gpu`（capture 管线）、`native_execution::run_profile_gpu`（攒批组装）、`capture_image` cascade 分支（快照管线，按一级模型 ordinal；级联 GPU 合同仍限 CUDA:0——cascade 网关 `device=="CUDA:0"` 未动，接线后 0 号会话行为不变）。`scheduler.rs` 关闭清理改调 `pipeline::release_for_shutdown`。测试调用点 `global()`→`for_device(0)`（6 处）。

**门揪出的二次缺陷与重设计**：首版在级联快照路径经 `lock(&model.session)` 读 ordinal——GPU 级联真机门（`gpu_cascade_public_entry_real_replay`）在持有 primary session 锁下提交（设备内存记账冻结会话的测试形态），自死锁挂起于 teardown 前的提交段。该路径的隐含合同是**不得锁 session**。重设计：`ModelHandle.cuda_ordinal`（AtomicU32 无锁镜像，加载时从 `Model::cuda_ordinal` 定值——热替换装载新句柄故镜像不会陈旧）+ `Plan` 构造时快照 ordinal，级联分支读 `self.cuda_ordinal` 零锁取管线；非级联 `capture_gpu` 维持既有 session 锁（其路径从未在外持锁下调用）。三个测试桩句柄初始化器（exports_tests/pool/swap_tests）补镜像字段。

**验证**：单卡 ordinal 0 全链回归（真机门全绿，见下）；`Model::cuda_ordinal` 与 selection 同源（device.rs 既有单测覆盖 selector→ordinal 重写链）。**诚实边界**：双 GPU/非 0 ordinal 并发管线（多管线共存、跨设备注册缓存隔离）为代码可达性修复，本机单 NVIDIA 卡无法实测——双卡验证列未测，接入方多卡部署前须补双卡门。
