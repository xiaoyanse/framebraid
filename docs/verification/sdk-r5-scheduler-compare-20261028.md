# R5 3.1 攒批调度对照与新旧取舍结论（2026-10-28）

目标卡 `.local/evidence/r5-31-batching-20261028/target.md`（测前固定）。DLL 与 [2.2 实测](sdk-r5-batching-live-20261028.md) 同批；ORT CPU + dynamic.onnx 合成批量负载（64 项/轮、8 项×8 次提交），交替 3 轮。

## 结果（轮 2 攒批组守恒破坏 40/64，按目标卡弃用该轮；其余轮 64 项全终态）

| 组 | 合格轮 P95（逐项完成延迟） | 合格轮端到端 |
| --- | --- | --- |
| 攒批启用（8/100ms） | 1.17ms / 1.93ms | ~1.2ms / ~1.9ms |
| 攒批关闭（逐项 AUTO） | 3.66ms / 1.44ms | ~3.7ms / ~1.4ms |

两组延迟均在 1～4ms 区间且轮间波动（1.44↔3.66）大于组间差；吞吐同为 64 项毫秒级完成。**结论：本负载（小模型、CPU、离线合成批量）下攒批无显著吞吐或延迟收益**——模型单次推理开销过低，调度窗口与合并开销互相抵消；该结论不外推真实检测模型、在线流或 GPU 后端，攒批在这些场景的收益保持未证（"主收益未证时保存取舍结论"，不判通过也不判失败）。

轮 2 守恒破坏（40/64）经独立探针复核（连续两轮 128 项满负荷提交零拒绝、全部成批）判定为**基准脚本自身缺陷**（提交时刻记录路径），非 SDK 行为；基准脚本修复后可复测，不影响本记录结论方向。机制正确性与功能面以 2.2 实测六场景 + 16 项合成单测 + 384 项 workspace 回归为准。

## 3.1 收口

新旧调度（攒批关闭=旧行为，启用=新路径）同预算对照完成：准入/等待/过期/取消语义由 2.2 与单测覆盖，吞吐/延迟对照如上（无显著差异），保护项（终态守恒、无失败）在合格轮全部满足。调度改动在关闭态零行为变化（默认关闭回归），开启态为可选优化路径。固定长跑不适用本项（用户裁决移出强制门槛）。
