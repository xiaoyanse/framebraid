# R3：RTSP像素队列与时间表实际容量

## 范围、目标与改前失败

评审基线`952d9f7`，对应R3 1.1j。MET-2 M-RECOVER/S5主目标是实际容器容量不超既有预留，保持当前队列/时间关联上限和最终内容；保护PTS/代次、采样、压缩隔离、预算及关闭。只在SDK内验证，不改AM-RT或现场设备、不发布。

新增测试先抽出原样的时间窗口操作以观察真实Worker，最初测试模块路径/借用编译错误已修正并保留日志，不将其当SDK缺陷。随后两项有效回归在未修实现上实际失败：

- 像素队列填入36项，VecDeque容量为64；既有控制存储只按36个Job预留。
- Worker连续记录10,000次接收时间，最终长度128却有256槽、4096字节容量；原帧字节许可仅2048。原因是先插入第129项触发扩容，随后pop并不收缩容量。

## 实现与量化

Pipeline在既有控制准入后try_reserve_exact(maximum)，并核实际容量；Worker在已有2048字节许可后预留128槽。时间表先淘汰再插入，保留相同最终128项顺序，不改变时间戳重复/缺失处理、参考链、采样或故障策略。空闲存储继续持有许可，最终缓冲先析构、许可后归还，未提高预算。

| 同机存储指标 | 改前 | 改后 |
| --- | --- | --- |
| 36项队列容量（Job=32字节） | 64 / 2048字节 | 36 / 1152字节 |
| 128项时间表容量（记录=16字节） | 256 / 4096字节 | 128 / 2048字节 |
| 两容器槽存储合计 | 6144字节 | 3200字节 |

合计少2944字节，仅指本机这两块SDK容器槽容量，不含结构本体、载荷共享、allocator和原生库，不是RSS或吞吐降幅。填满队列和10,000次滚动后容量不超预留；时间表首尾仍为`(9872,29872)`/`(9999,29999)`，drop后相应控制/帧字节均回到测前。固定预留会把分配提前到启动，不宣称所有阶段都少分配或更快。
