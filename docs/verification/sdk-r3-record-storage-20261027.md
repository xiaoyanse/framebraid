# R3 推理请求表实际存储计费

日期2026-10-27，评审基线`87baecd237b68816c90793b5203774bc77f2a17e`；仅SDK main串行本地修改，未改AM-RT/现场设备/公开制品。任务R3 1.1m，评价按MET-2；BP10和父任务1.1不由本阶段整体关闭。

## 问题与机制

原推理记录表有条目数限制，但HashMap实际保留容量未计控制字节。真实旧DLL在控制上限1或64字节时仍接受并完成推理，不能以“数量有界”认定字节审计完成。

改为按ID有序的小型连续表，分配前按实际槽容量占控制字节，增长时先保留旧、新存储重叠；分配失败保持旧表。删除/TTL清理只删记录，不释放仍占用的容量额度；服务销毁才退账。数量限制不提高，不给空闲槽伪造外持结果或控制快照项目，不增加Context.buffers关闭屏障。结果载荷与在读输入继续原计费/生命周期。

增长拒绝发生在旧请求替换、ID发布前；已保留容量可复用，降低策略不追溯撤销旧存储。查找为二分，删除/插入有界移动记录，代价需以同负载数据观察，不宣称全面提速。State本体/通用服务索引仍属BP10后续，allocator及ORT内部内存不冒充本次字节计费。

## 定向与真实DLL检查

- 本机单测槽布局80字节；1槽80、2槽160，1→2增长峰值240。额度239时拒绝、旧长度/容量/账均保持；240允许增长。清空两项后仍计160，销毁后归零。3项非二次幂上限实际capacity=3，不偷偷扩4。
- 表存储与公开快照共用控制字节，但快照items/Context.buffers只计真实快照；原快照释放后表存储继续计费。21项全特性、20项无默认特性单测通过，其中新增3项存储测试。取消/清理逻辑的隔离测试构造明确不代验分配预算。
- `test-inference-record-storage.py`：旧DLL在1/64字节返回OK且有ID；新DLL均返回8/resourceExhausted且ID=0。64KiB下输出逐字节正确，两次顺序请求ID连续；已空闲表不阻止Closed。
- 真实保留输入归还屏障：第一项仍运行、第二项排队，缩控制预算后第三项需扩容，明确拒绝；释放屏障后原两项都成功，无旧请求被错误替换。复用已存容量的下一请求序号连续，输入retain/release=[1,1]。
- 原生/SPLIT/AUTO、64项原生批次、固定尾批拒绝、逐项回执/取消、等待/恢复、准入deadline及32项回执边界均通过；五类模型档案明确`profileImages skipped`，不代验R4。
- 通知fetch/ack/release、禁重入、慢通知隔离、注销/关闭屏障、线程回收及统计拥有者通过；压力含未取结果、慢通知和真实共享帧输入通过。CPU分类/Context隔离三场景各三轮9/9健康准入，超额/拒绝ID和拥有者平衡。
- 六轮忙模型取消/替换清理：健康准入0.0293～6.907ms，排队终态0.0643～6.9377ms，均在忙模型仍运行时完成，低于原100ms保护线。收尾queue_items/bytes及外持0，线程active/peak=4≤16。

测试脚本初稿误在极小控制额度下调用需要控制快照的query、且使用了不存在的destroy名称；已改为结果fetch轮询和既有关闭工具，原错误保留，未计为SDK运行故障。
