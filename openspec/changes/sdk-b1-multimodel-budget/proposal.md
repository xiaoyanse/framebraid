# Proposal: SDK B1 — 多 Model ctx 预算分配策略（错峰执行+账目精估）

## Summary

多 Model 场景下 ctx 级预处理预算（64MiB 包络）的分配与调度策略演进：
**执行错峰调度**（ctx 级执行槽，多 Model 执行期份额不同时叠加）+ **执行份额
账目精估**（24B/px 口径按真实驻留复核）。目标：解锁双 Model 批 3/批 4 形态
（现状 75% 提交拒绝），SDK 层吞吐上限 57.9 → 120-150 items/s 区间（8 路
25fps world 双输入 PROFILE 口径）。**零 ABI 变更**：am_limits_t 结构、总量
语义、拒绝语义全部不变。

## Motivation（2026-11-12 评估实验证据）

- 双 Model×批 2 = **97.7 items/s 零拒绝（+69% vs 单 Model 57.9）**——多
  Model 并行增益已被 SDK 真路径实证，且为预算内唯一稳定点。
- 批 3/批 4 形态被 ctx 预算挤兑（35.0/49.8 items/s + 74-75% 拒绝，丢帧无
  产品意义）：挤兑主项=执行期份额实测 **≈9.8MB/项**（批 E 24B/px×640²
  口径吻合），双 Model 同相窗口执行重叠时叠加超限（批 3=77.4MB、批 4=
  103MB vs 64MiB）。
- repro 层双流并行 177 items/s（批 F）证明 GPU 侧有余量——缺口在 SDK 预算
  的分配策略，不在算力。
- `amv_set_limits` 只能收紧（合同约束），预算不可放大——分配策略是唯一
  合法路径。

## What Changes

1. **执行错峰调度**：ctx 级执行槽（互斥/信号量）——一个 Model 的执行期
   份额入账期间，其他 Model 窗口排出的批延迟进入执行（挂起份额照常入账，
   执行份额等槽）。峰值账目=单 Model 执行份额 + 全部 Model 挂起份额：
   批 3=29.4+18.6=48MB ✓、批 4=39.2+24.8=64MB 贴线（配合第 2 项收敛）。
2. **执行份额账目精估**：24B/px 口径复核——GPU 直传路径（assemble_frames
   D2D）的"ORT 输入副本"真实 host 驻留、CPU 合并缓冲实际生命周期；若实测
   低于现行口径则按实测收敛（批 E 分期计费同型重估先例：重估不等于放宽
   护栏，拦泄漏能力保持）。
3. 零 ABI/零 FFI 新增；纯 vision 域内部分配与调度策略。

## 护栏不弱化承诺（决策人红线，2026-11-12 立项令）

- ctx 总量 64MiB 不变、三层（class/context/executor）结构不变、满照拒
  语义不变、取消/TTL/排空全量归还不变。
- 实施中任何一步发现策略改动导致护栏弱化（OOM 风险回归、守恒破缺），
  **立即停下上报，不硬闯**。
- 批 E 守恒测试族全量保留并扩展到多 Model 场景。

## Impact

- 范围：vision 域（executor 执行准入、预算账本、攒批协调），AM-RT 零改动。
- 门禁 **L2**（业务功能类：单模块逻辑，无 ABI/协议/DB 触发）——要件：
  关键路径单测（多 Model 守恒族）+ 关键集成点真装配测试（双 Model e2e）+
  代码取证。
- 量化（MET-2）：主目标=双 Model 批 3/批 4 吞吐（对照批 2 基线 97.7 与
  单 Model 57.9）；保护指标=尾延迟（错峰等待进 P99 预算）、单 Model 路径
  零回归、预算守恒。承诺口径：批 3/4 解锁后上限向 120-150 抬升（GPU 双流
  服务率约束下的 SDK 层折减，不承诺 repro 层 177）。
- 风险：错峰使第二 Model 批执行时延增加（等槽时间）——尾延迟进保护指标
  量化；若批 4 贴线形态实测仍触发拒绝，如实记录稳定边界（批 3 解锁即可
  交付，批 4 边界入档）。
